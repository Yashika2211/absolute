# Streamline

A production-style real-time recommendation system with a streaming feature store,
built on the [RetailRocket](https://www.kaggle.com/datasets/retailrocket/ecommerce-dataset)
e-commerce clickstream (2.76M events, 1.4M visitors, 235K items).

The focus is on what makes recommenders hard in production: **point-in-time
correctness**, **no training/serving skew**, **time-based evaluation**, and
**measured latency**. Only a few features are built, and each one is tested.

## Architecture

```mermaid
flowchart LR
    subgraph Ingest
        CSV[(RetailRocket<br/>events.csv)] --> SIM[Event simulator<br/>replay at N x]
    end
    SIM -->|keyed by user| RP[[Redpanda<br/>Kafka API]]

    subgraph Features["Feature store"]
        DEF{{Feature definitions<br/>single source of truth}}
        RP --> BW[Bytewax<br/>stream job]
        DEF --> BW
        DEF --> BF[Offline backfill]
        BW --> REDIS[(Redis<br/>online store)]
        BF --> PQ[(Parquet + DuckDB<br/>offline store)]
    end

    subgraph Training
        PQ --> PIT[Point-in-time<br/>dataset builder]
        PIT --> TT[Two-tower<br/>PyTorch]
        PIT --> LGB[LightGBM ranker]
        TT --> FAISS[FAISS HNSW index]
        TT -.-> MLF[(MLflow<br/>tracking + registry)]
        LGB -.-> MLF
    end

    subgraph Serving["Serving (Phase 4)"]
        API[FastAPI<br/>/recommend/user_id]
        REDIS --> API
        FAISS -->|~500 candidates| API
        LGB -->|rerank| API
        API --> PROM[Prometheus] --> GRAF[Grafana]
    end
```

**Status:** Phases 1–3 are complete:
- **Phase 1:** ingest, the simulator, time-based evaluation, baselines, the two-tower model and
  MLflow tracking.
- **Phase 2:** the streaming feature store (Bytewax → Redis online, backfill → Parquet/DuckDB
  offline, skew tests).
- **Phase 3:** FAISS retrieval and a LightGBM reranker, evaluated at request time.

Phases 4–5 are planned (see [Roadmap](#roadmap)).

## Results

### Retrieval (Phase 1): next 14 days, scored at the test cutoff

Test window: the last 14 days (2015-09-04 02:59 UTC onward). Validation: the 14 days before that
(from 2015-08-21 02:59 UTC). Metrics are averaged over the **14,774 warm test users**
(127,251 cold users with no prior events are not scored; see Design decisions).
New-item columns score the 12,486 users who touched at least one item they had never seen before.
The two-tower row is mean ± std over 3 seeds. The popularity window (14 days) was chosen on validation.

| Model | Recall@50 | NDCG@10 | MRR@50 | New-item Recall@50 | New-item NDCG@10 | Val Recall@50 |
|---|---|---|---|---|---|---|
| Popularity | 0.0193 | 0.0051 | 0.0055 | 0.0153 | 0.0038 | 0.0211 |
| Recently viewed + popularity | 0.1880 | 0.1682 | 0.1824 | 0.0153 | 0.0038 | 0.2074 |
| Two-tower (3 seeds) | 0.2220 ± 0.0004 | 0.1687 ± 0.0008 | 0.1796 ± 0.0007 | 0.0745 ± 0.0011 | 0.0254 ± 0.0007 | 0.2385 ± 0.0013 |

Source: [`reports/results.md`](reports/results.md) and [`reports/results.json`](reports/results.json),
generated by `make train` at commit `7f9a937`. All runs, including per-epoch validation curves, are in MLflow.

**Reading the table**
- The two-tower model improves Recall@50 by **18% relative** over the strongest baseline
  (0.222 vs 0.188), and is **11.5× better** than global popularity.
- On **new items** it gets about **4.9× the recall** of either baseline (0.075 vs 0.015). That's the
  retrieval capability the later ranking stage depends on. For new items, *Recently viewed* is
  identical to popularity, since removing seen items leaves only its popularity backfill.
- At the very top of the list it only ties: NDCG@10 is 0.169 vs 0.168, and MRR is slightly
  *lower* (0.180 vs 0.182). Recency of the user's own items is hard to beat at rank 1. The
  Phase 3 LightGBM ranker is designed to close this gap by combining retrieval scores with the
  streaming recency and session features below.
- Metrics are exact brute-force retrieval over the full 153K-item vocabulary. FAISS results
  are in the next table.

### Retrieval + ranking (Phase 3): at request time

This is what serving will do, replayed at historical moments. A request is a real moment
when a returning user shows up (one sampled event at time *t*, one request per user). The
system:
1. Embeds the user's last 50 events before *t* with the user tower.
2. Retrieves 500 items from **FAISS HNSW** and adds the user's recent items.
3. Builds 22 features **as of *t*** (retrieval, user-item history, and the Phase 2 streaming
   user/item features).
4. Reranks with **LightGBM LambdaRank**.

Relevant items are those the user touches in **[t, t + 30 min)**, clipped to the split, with
1.30 items per request on average.

The ranker trains on requests from the validation window, using a two-tower model fit only on
train. Of the 8,000 sampled requests, those with at least one relevant candidate carry signal:
4,337 are used for training and 1,039 (the latest 20% by time) for early stopping. The table
scores 8,000 requests from the test window, using the two-tower model refit on train + val. This is a different task from the Phase 1 table, so the
numbers aren't comparable across the two tables.

| Method | Recall@50 | NDCG@10 | MRR@50 | New-item Recall@50 | New-item NDCG@10 |
|---|---|---|---|---|---|
| Popularity (14d) | 0.0207 | 0.0052 | 0.0047 | 0.0158 | 0.0035 |
| Recently viewed + popularity | 0.3988 | 0.3796 | 0.3998 | 0.0158 | 0.0035 |
| Two-tower, exact | 0.5191 | 0.3738 | 0.3773 | 0.3009 | 0.1197 |
| Two-tower, FAISS HNSW | 0.5191 | 0.3738 | 0.3773 | 0.3009 | 0.1197 |
| **Two-tower + recent → LightGBM** | 0.5677 | 0.4331 | 0.4369 | 0.3040 | 0.1229 |

Source: [`reports/ranking.md`](reports/ranking.md) and [`reports/ranking.json`](reports/ranking.json),
generated by `make rank` (single seed).

- **The reranker beats the best single source on every top-of-list metric.**
  - NDCG@10: 0.380 → **0.433** (+14%)
  - MRR: 0.400 → **0.437** (+9%)
  - Recall@50: 0.519 → **0.568** (+9%)

  This is the gap Phase 1 left open: the ranker learns when to promote the user's own recent
  items over new retrievals. On new items it only ties the two-tower (Recall@50 0.304 vs 0.301).
- **FAISS HNSW costs no measurable accuracy.** It recovers 99.5% of the exact top-500 and
  99.99% of the exact top-50, and the exact and HNSW rows match to 4 decimals. HNSW needs
  `efSearch` above the number of results requested. With `efSearch` = 256, top-500 overlap was
  92.7%; at 800 it's 99.5%.
- **Candidate recall is 64.2%.** That's the ceiling for any reranker on this candidate set
  (about 500 candidates per request), so the biggest headroom left is in retrieval.
- **Model-side latency per request (p50 / p99, measured on an Apple-silicon laptop CPU):**
  - user tower: 0.17 / 0.24 ms
  - HNSW top-500: 2.21 / 3.05 ms
  - LightGBM over about 500 candidates: 0.91 / 1.30 ms

  That's about 4.6 ms at p99 before Redis and HTTP overhead, comfortably inside the 50 ms
  target. Phase 4 will measure the full service under load.
- **Limitations.**
  - Early stopping kicks in after only 12 trees, and most of the gain comes from the retrieval
    rank and score.
  - The streaming features rank lower in importance (the top 10 are in `ranking.json`) because
    one request per user at a random moment rarely lands mid-session.
  - Single seed. Multi-seed confidence intervals and request sampling weighted by sessions are
    the next experiments.

## Streaming feature store

14 features plus the user's **last-50-event history** are declared once in
[`features/definitions.py`](src/streamline/features/definitions.py). Each is a function of
*(entity, as_of)* over events **strictly before** `as_of`. The history feeds both the two-tower
user tower and the ranker's user-item features, so serving reads exactly what offline
evaluation used.

| Entity | Features |
|---|---|
| User | `user_events_5m`, `user_events_1h`, `user_carts_1h`, `session_events`, `session_distinct_items`, `session_carts`, `session_duration_ms`, `last_event_age_ms` |
| Item | `item_views_5m`, `item_views_1h`, `item_views_24h`, `item_carts_1h`, `item_carts_24h`, `item_purchases_24h` |

A session is a run of a user's events with gaps of at most 30 minutes. It counts as the
current session while the last event is at most 30 minutes old.

**Online/offline skew check.** `make skew-check` publishes real events to a fresh Redpanda
topic, runs the Bytewax job into Redis, and compares every user and item against the offline
engine at 6 times after the stream ends (+1 ms, +2 min, +10 min, +30 min 1 ms just past the session gap, +2 h, +24 h):

| Replay slice | Events | Users | Items | Values compared | Mismatches | Bytewax ingest (1 worker) |
|---|---|---|---|---|---|---|
| 2015-09-04, 7 days | 131,571 | 77,005 | 49,447 | 5,938,362 | **0** | 22,121 events/s |

Source: [`reports/skew.json`](reports/skew.json). The values compared include the 50-event
history of every user. Ingest dropped from about 44K to 22K events/s once each event also
updates the history set; it's still far above the dataset's peak rate.

**Offline backfill.** `make backfill` computes all 14 point-in-time features for every one of
the 2,755,641 events in 9.4 s (about 293K rows/s, vectorized) and writes 139 date partitions
(51 MB of Parquet), which DuckDB queries with partition pruning.

## Quickstart

Prerequisites: Docker, [uv](https://docs.astral.sh/uv/), and a Kaggle API token.

```bash
make install   # uv sync + pre-commit hooks
make up        # Redpanda, Redpanda Console, Redis, Postgres, MLflow
make data      # download events.csv from Kaggle -> data/raw, build parquet
make eda       # dataset summary -> reports/eda.md
make train     # Phase 1 retrieval (3 seeds) then Phase 3 ranking, logged to MLflow -> reports/
make rank      # Phase 3 only: FAISS + LightGBM at request time -> reports/ranking.md
make simulate  # replay events into Redpanda (SPEEDUP=1000 START_DATE=2015-09-04)
make stream    # Bytewax: clickstream topic -> Redis online store (run next to `make simulate`)
make backfill  # point-in-time features for every event -> data/offline (Parquet, DuckDB)
make skew-check  # end-to-end online vs offline diff on real events (SKEW_HOURS=168)
make check     # ruff + mypy + pytest (what CI runs)
make test-integration  # tests against the live stack
```

| Service | URL |
|---|---|
| MLflow | http://localhost:5001 |
| Redpanda Console | http://localhost:8080 |
| Kafka API | 127.0.0.1:19092 |
| Redis | localhost:6380 |

**macOS note.** The torch, faiss and lightgbm wheels each bundle their own OpenMP runtime.
Two copies in one process abort or deadlock, and serving needs FAISS and LightGBM together.
`make install` runs [`scripts/fix_macos_openmp.py`](scripts/fix_macos_openmp.py), which points
the bundled copies at Homebrew's `libomp` (`brew install libomp`). A guard raises a clear
error if the fix is missing. On Linux this step does nothing.

**Kaggle credentials.** Create a token at kaggle.com → Settings → API → *Create New Token*.
Then either save the token string to `~/.kaggle/access_token` (or `export KAGGLE_API_TOKEN=...`),
or save the downloaded `kaggle.json` to `~/.kaggle/kaggle.json`. `make data` prints
these instructions if no credentials are found.

`make serve` and `make loadtest` are reserved for Phase 4.

## Design decisions

- **Time-based split, not random.** The last 14 days are the test set, the 14 days before them are
  validation, and everything earlier is training. A random split would leak the future into
  training and inflate every metric.
- **Fit on the past, predict the next window.** For validation, models are fit on train and
  predict the validation window. For the test, models are refit on train + val with the settings
  selected on validation, then predict the test window. The test set is only used once, for the
  final numbers.
- **Warm users only.** 90% of visitors in a 14-day window have no earlier events. Without
  history every model falls back to popularity, so the headline metrics cover users with at
  least one prior event, and the cold-user count is reported next to them.
- **New-item metrics.** About 14% of target interactions are items the user already touched.
  Recommending the user's own history is therefore strong, and it's included as an explicit
  baseline. The `New-item` columns remove seen items from both the recommendations and the
  relevant set, to measure discovery separately.
- **Point-in-time correct training.** Each two-tower training example is (the user's events
  *strictly before* event *t*, the item at *t*). `tests/test_two_tower.py` checks that no
  example's history includes the target event, a later event, or another user's events.
- **Two-tower model.** The user tower mean-pools the last 50 events (item + event type +
  recency position) and concatenates the most recent event, followed by an MLP. The item tower
  is an item embedding shared with the user tower plus a residual MLP. Training uses in-batch
  sampled softmax with **logQ correction** (so the model doesn't just learn popularity) and
  masks duplicate items within a batch. Model selection uses early stopping on validation
  Recall@50. Scoring is currently exact dot product; FAISS replaces it in Phase 3.
- **The history-based user tower** (rather than a per-user ID embedding) works for any user
  with recent events, including ones unseen at training time. It's also the shape the online
  feature store will serve.

**Feature store**

- **Declared once, two engines, proven equal.** The feature definitions hold the windows,
  event filters, session gap and a small reference implementation. Two engines implement them,
  because the access patterns differ: the online engine does incremental per-event updates, and
  the offline engine does vectorized computation over millions of (entity, time) points. Skew
  between them is ruled out by tests, not by assumption:
  - Unit tests replay synthetic streams (gaps just under, exactly at and just over 30 minutes,
    same-millisecond events, 24-hour rollovers), comparing online and offline at every checkpoint.
  - A test runs the real Bytewax dataflow, including malformed messages.
  - `make skew-check` diffs the engines on real traffic through Redpanda.
  - I checked that the tests catch skew by deliberately breaking each engine (wrong trimming,
    wrong session gap on either side). All three bugs were caught.
- **Online store layout.** Per-entity Redis sorted sets are scored by event time. Writes are one
  Lua script per event, so they are atomic. They are also **idempotent** (ZADD of an existing
  member is a no-op), so at-least-once delivery and full topic replays can't double count, and
  the Bytewax job stays stateless and can be restarted freely. Events are trimmed by *event
  time*, keeping the longest window plus the user's whole current session. TTLs exist only for
  garbage collection, so correctness never depends on wall-clock time, even when replaying at
  1000×. Reads are exact for any `as_of` at or after the entity's latest event, i.e. "now" in
  serving. The stream's current time is kept as a `watermark` key.
- **Point-in-time training data.** Each backfilled row has the features *as of that event's own
  timestamp*, computed from strictly earlier events. A leakage test adds and removes arbitrary
  events at or after `t` and asserts that the features at `t` are unchanged.
- **Keyed by user.** The simulator partitions by `user_id`, so each user's events are consumed
  in order. Item sets are order-independent, so interleaving across partitions can't cause skew.

```
  config.py            settings (env-overridable)

reports/               generated EDA, results and skew reports (committed, real numbers only)
```
